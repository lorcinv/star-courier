# 星际快递 · 场景化营业日迭代

状态：开发中的可玩切片，尚未作为最终成品发布。旧版 v0.1 的截图、压缩包与说明不能代表本轮完成程度。

## 本轮体验目标

玩家在一家小型轨道邮局经营自动配送业务。柜台选择货物，工位设计装置，试飞验证，正式配送承担后果，回店读客户反馈，再把利润投入下一天。

画面参考是用户提供的 Denshattack! 宣传美术的高饱和配色、强轮廓和大曲线构图；经营节奏借鉴 Dave the Diver 的出发与回店交替。场景、人物、模型、音乐和规则为本项目原创实现，不使用参考游戏素材，也不声称复刻其完整系统。

## 已接通的营业日

- 每天两位有限客户带着实物包裹入店；柜台可接下或婉拒委托。
- 同时只有一份已接委托。委托 ID 唯一，状态为 available → accepted → in_flight → settled；已接后退回会减 1 声望。
- 包裹从客户处移到柜台，再移向装配区；客户排队、离开与营业状态关联。
- 飞行器与固定发射台分别装配。25 种模块保留独立物理/逻辑功能；货舱为额外必需件。
- 参数按模块类型设定，固有强度不能免费提高。结构连接、定向动力、能源流和信号线影响自动飞行。
- 同一委托试飞与正式配送使用相同航线、载重与种子。试飞不改变余额、声望或库存。
- 正式发射先显示费用口径与约束，再确认。先保存委托和设计快照，才开始运行。
- 正式配送每单结算一次。收入、能源、弹药、维修和未回收部件分别入账；同一件不会同时算弹药与损失。
- 本轮采用自动整备服务：采购增加可同时安装数量；正式结算支付实际消耗/补件/维修，装置恢复为原图纸。蓝图不会增加库存。
- 白天不能采购；主动收工后进入夜间。校准充电台每级增加 15% 有限储能，并在场景显示灯级；实际耗能仍计费。
- 次日刷新两份委托。已结算单不能重复领取、重试领奖或靠重载重复结算。
- 重启正式飞行按持久化设计、种子和整数物理步数重放到检查点，继续同一委托。

## 可验证的首单选择

实际种子 100、标准种子货物、起始库存：

| 方案 | 航时 | 消耗 | 完整度 | 净利润 |
|---|---:|---:|---:|---:|
| 原装 12 N | 8.792 s | 320 J | 100% | ¥107 |
| 原装降低至 3 N | 13.425 s | 209.63 J | 100% | ¥127 |
| 加备用电芯，24 N | 7.217 s | 620 J | 100% | ¥53 |

过度加宽的梁会碰到碎石门。过载 40 N 方案即使抵达，也可能因丢件净亏损。反向喷口是可预见的失败；只纠正方向即可恢复成功。首条航线主要教外形和能耗取舍，并不声称所有护甲选择在该航线都有价值。

## 本轮验证与限制

- 有独立物理、参数不变量、营业日、持久化事务、真实控制器和代表航线测试。
- 实际 Godot GUI 截图与原生鼠标/键盘测试独立于脚本截图；原生测试已找出脚本截图未暴露的首次提示框尺寸问题，正在修复与复测。
- 场景采用 Godot 3D、正交侧视镜头、硬色阶材质与描边；Blender 场景源文件和部件源文件保留。
- 经营是有限客户与主动推进的营业日，不包含餐厅式限时手速服务、员工排班或完整城市经济。
- 仿真是确定性的平面自定义刚体系统，不是通用三维刚体沙盒。
- 重启恢复采用确定性重放，而非保存引擎刚体状态；最多回放上个检查点后的不足一秒。
- 当前仍需继续验证：新手引导、失败归因、不同分辨率、所有阶段的实际输入、长时间游玩与更多路线的平衡。
- 本轮未制作或发布最终安装包。Windows 运行情况必须在新的导出完成后重新区分“成功导出”和“原生 Windows 实测”。
